# R2: spec v0.3 in the library, then GBNF grammars

Read `RULES.md`, then `SPEC.md`, which is now **v0.3**. Read sections 1, 3, 6, 7 and 8 closely, because they changed. `SPEC.md` is the only authority on behaviour. Where it doesn't answer something, stop and ask (rule 5).

There are three parts, done in order.

## Part A: bring the library up to v0.3

1. **Raw values** (section 3):
   - remove the `\n` and `\s` escapes; they are now errors;
   - add `\r` raw values, including data lines that span physical lines;
   - `\r` in a field that isn't `str` or a `list[str]` item is an error;
   - inside a raw value, only `\|` and `\\` are escapes;
   - an empty raw value is an error.
2. **Line type** (section 1): a line that starts with `schema:` and contains a `|` is a data line.
3. **Outside schemas** (section 6). Add exactly these public functions, keeping `decode` and `encode` as they are:
   - `decode_with(schemas: &str, text: &str) -> Result<DecodedFile, StructError>`;
   - `encode_with(schemas: &str, file: &DecodedFile) -> Result<String, StructError>`.

   `schemas` is one or more `schema:name{...}` definition lines, one per line. Errors inside `schemas` report their line and column within `schemas`, and the message says the error was in the outside schemas.
4. **Canonical form** (section 7): make `encode` and `encode_with` write exactly that form, including the new float rule.

## Part B: grammars

Add these public functions:

- `gbnf(schemas: &str) -> Result<String, StructError>`: the **full** form, as GBNF text.
- `gbnf_triggered(schemas: &str, trigger: &str) -> Result<String, StructError>`: the **triggered** form.

Before writing the triggered form, read the llama.cpp server source in `C:\Users\Ashman Das\Documents\turboquant-llama-cpp` (read only) and find out exactly how lazy grammars and their triggers work:
- the request fields;
- the trigger types;
- whether the grammar sees the trigger text itself, or only what comes after it.

Write your findings in `research/r2-lazy-grammar.md` and build the triggered form to match them. If they leave a real choice open, stop and ask.

The grammar must allow **only** the canonical form (sections 7 and 8), meet the completeness and soundness rules in section 8, and load without error in llama-server.

## Part C: tests

All runs use `cargo test --offline`, except the model smoke test, which is a Python helper in `bench/r2/`.

1. **Update every existing test for v0.3.** Spec examples, byte for byte, now include the raw-value example and the outside-schema rules.
2. **Negative tests,** with the exact line, column and full message:
   - `\n` and `\s` used as escapes;
   - `\r` in an int, float, bool and enum field;
   - an empty raw value;
   - an unknown escape inside a raw value;
   - a raw value with no closing `|` before the end of the file;
   - with several outside classes, data before the first schema line;
   - redefining an outside class;
   - an error inside the `schemas` argument.
3. **Float formatting:** a table test of at least 40 values checking the exact canonical text. It must cover each side of `0.0001` and `10000`, whole numbers, negatives, `0`, `-0`, `NaN`, `inf`, `-inf`, the largest and smallest `f64`, and subnormals.
4. **Round trips, at least 5,000 cases.** Extend the random generator with:
   - values that need `\r`: a line break, an edge space, an edge tab;
   - raw values whose inner lines start with `>`, `schema:` or spaces;
   - text values starting with `schema:`;
   - floats spread across the whole `f64` range.

   Run every case twice, once with `encode`/`decode` and once with `encode_with`/`decode_with` (one and several outside classes). Report the counts for every edge case, the old ones included.
5. **A GBNF checker inside the test suite.** Write a small GBNF reader and matcher, standard library only, that covers exactly the parts of GBNF your generator uses, and keep the generator to a small part of GBNF. Then:
   - **completeness:** for every round-trip case, the canonical `encode_with` output must be accepted by its `gbnf` grammar;
   - **soundness:** write a random walker that produces text from the grammar, at least 5,000 samples across the random schemas. Every sample must decode with `decode_with` without error, apart from the one `int` exception in section 8, which you count and report;
   - **canonical only:** at least 10 non-canonical variants must be rejected by the grammar while `decode_with` still accepts them. Include a space after `|`, an unneeded index, a blank line, a `\r` that isn't needed, `1e2` for a float that should be `100`, `+5` in a float, and a trailing space before a line break.
6. **Model smoke test** (`bench/r2/smoke.py`). This follows rule 7: check `nvidia-smi` first, run one model at a time on `127.0.0.1:8090`, and stop the server afterwards.
   - **Schemas:** the three R1 datasets' schemas, plus a two-class schema in which one field holds code (needs `\r`).
   - **Prompt:** the schema lines, one sentence explaining the format, and a short task: write 5 records from the given notes. Keep the prompt identical for every model. Put the prompt text in the report.
   - **Full form, no thinking:** `Llama-3.2-1B-Instruct-Uncensored.Q4_K_M.gguf`, `gemma-4-E2B-it-Q4_K_M.gguf` and `LFM2.5-8B-A1B-Q4_K_M.gguf`. Gemma and LFM are thinking models, so for this form turn thinking off through their chat template, and say how you did it.
   - **Triggered form, thinking on:** `gemma-4-E2B-it-Q4_K_M.gguf`, `LFM2.5-8B-A1B-Q4_K_M.gguf` and `Mellum2.1-12B-A2.5B-Thinking-Q4_K_M.gguf`.
     - The trigger is each model's real end-of-thinking text, normally `</think>`. Check it in each model's chat template and report it. If a model's tag differs, use that model's tag.
     - Keep Mellum's experts on the CPU if it doesn't fit in 8 GB.
     - Report the thinking tokens separately from the Struct tokens.
   - **Runs:** 5 generations per schema per model, temperature 0.7, a fixed seed per run, and a 1,500-token cap.
   - **Report per run:**
     - whether the output decodes with `decode_with`;
     - the number of records;
     - output tokens;
     - whether it hit the token cap. Run-on output is a real finding; don't hide it.

   This is a smoke test that the grammar works with real models. It isn't a quality benchmark; that's R4.
