# R4: retrieval accuracy across formats

**Status: decided, waiting to build.** The Bonsai run3 report is verified first (see Decisions).

R1 measured what each format costs in tokens. R4 measures whether a model can **read** each format: the same data, the same questions, and only the format changes. Writing Struct is a separate skill, already tested in R3.

Read `milestones/RULES.md` and `SPEC.md` first.

## Formats (7)

1. Minified JSON
2. TOON (per its spec; R1's fixtures already have it)
3. YAML
4. TSV
5. XML-style tags
6. Plain `key: value` lines
7. Struct (typed, with schema: the `.v02.stc` form from R1)

Encoders go in `bench/r4/formats/` (standard library only). Every encoding must hold exactly the same data. Prove it: decode each encoding back to the source data, or for formats with no decoder, check it field by field against the source. Any format that can't hold the data without loss is reported, not quietly patched (see open questions).

## Data (4 datasets)

- R1's three shapes, from `bench/r1/fixtures/`: flat tabular (20 rows × 5 columns), nested fixed and nested variable.
- One bigger flat table of about 100 rows, made by a deterministic script (fixed seed), using the same columns as flat tabular.
- The data must include nulls, and some empty values if the formats allow them, so the null questions have something to find.

## Questions

- About 12 per dataset, mixing four kinds:
  - **single lookup:** one value by id;
  - **nested lookup:** a value inside a list or sub-record (not for the flat datasets);
  - **count or filter:** "how many records have status refuted?";
  - **null or missing:** "which record has no year?"
- **Same questions for every format.** Questions and answers are generated once from the source data, never from any one format's encoding, and saved to `bench/r4/questions.json`.
- Answers in the ground truth come from the source data only.

## Model and setup

- **Ternary Bonsai 2 27B** only, thinking on.
- Server: the prism fork at `C:\Users\Ashman Das\Documents\prism-llama-cpp`, launched with the maintainer's flags plus `--reasoning-budget 8192`. KV cache `q4_0`. Port 8090, per RULES rule 7. State the exact launch line in the report.
- Sampling, thinking mode: temperature 1.0, top_p 0.95, top_k 20, min_p 0.05, presence_penalty 0.0, repeat_penalty 1.0.
- `/v1/chat/completions` with the model's own template and `enable_thinking: true`. No prefills, no output cap, a 20-minute safety limit per request.
- **One request per format and dataset**, with all its questions asked together. The model answers as a numbered list, one short answer per line. TSV and `key: value` run only on the two flat datasets (see Decisions), so 7 × 2 + 5 × 2 = 24 requests per seed.
- **5 seeds:** 42–46, so 120 requests. Time depends on thinking length, capped at 8192 tokens per request.
- The prompt is identical for every format except the data block and one line naming the format. Show the full prompt text in the report.

## Scoring

- **Normalized match.** Lowercase, trim, strip surrounding quotes, collapse whitespace, then compare. The point is whether the model saw the data point, not how it writes it.
- **No value:** when the true answer is no value, only an explicit `null`, `none`, `~` or `n/a` counts as correct. A blank or missing answer is always wrong (decision 9).
- **List answers:** comma-separated, compared as a set (order ignored). Every item must match, with nothing extra.
- No partial credit. A missing or unparseable answer counts as wrong.
- If the thinking budget runs out, the answer is still scored as given. Count and report how often that happened, per format.

## Report: `research/r4-retrieval.md`

- Accuracy per format, per dataset, and per question kind, with counts (for example 52/60), not only percentages.
- Input tokens per format, from `/tokenize`, next to accuracy, so cost and accuracy can be read together.
- Thinking tokens per format: mean and max.
- Every wrong answer, listed with the question, the expected answer and the model's answer.
- Mean accuracy per format across seeds, and the spread.
- No causal claims nobody tested. Describe what happened, not why.

## Decisions (maintainer, 2026-11-21)

1. **Nested data in TSV and `key: value`:** skipped. Neither format has a standard way to hold lists or sub-records, so both run only on the two flat datasets, and the report lists them as "can't hold this shape" for the nested ones.
2. **No value:** any null word counts (see Scoring).
3. **List answers:** comma-separated, order ignored (see Scoring).
4. **Reasoning budget:** 8192.
5. **Order:** the Bonsai run3 report is verified first. R4 is built after that, and run only after its build is verified.

## Build decisions (maintainer, 2026-11-21, after the first build)

6. **Nulls in R1's datasets:** don't edit `bench/r1/fixtures/`. R4 uses its own copies of flat tabular and nested fixed, in `bench/r4/data/`, with a few nulls added (deterministic, fixed seed). Null questions on every dataset ask about real empty values in the data, never about records or fields that don't exist.
7. **XML null:** an empty tag, for example `<year/>`. No `null` attribute and no `null` text.
8. **`key: value` records:** separated by a `---` line.

## Review decisions (maintainer, 2026-11-21, after `research/r4-build-review.md`)

9. **Blank answers:** a blank or missing answer is always wrong, including when the true answer is no value. Only explicit null words count.
10. **Normalization, extra:** also strip markdown bold and italics (`**`, `*`, `__`, `_` wrapping the answer or the item number) and one trailing period before comparing.
11. **Several defensible forms:** for yes/no-style fields, accept yes/no, true/false and 1/0. For empty lists, accept `none`, `empty`, `[]` and the null words. No format is favoured.
12. **XML empty lists:** a plain empty tag (`<subnotes/>`), with no `type` attribute. XML then can't tell an empty list from no value; that is a real limit of plain XML. The no-loss check notes this for XML only, and the report says so.
13. **Mechanical fixes from the review (no design choice):**
    - the recorded launch line uses `--port 8090` (not `-p`, which is the prompt flag) and is the exact line used;
    - failed requests (HTTP error, timeout, no answer text) are not marked done; a resume reruns them, and every failure is recorded and reported;
    - budget exhaustion is counted from thinking tokens reaching the 8192 budget, not from `finish_reason`;
    - `metadata.json` is included in SHA256SUMS;
    - the report includes accuracy per format by question kind, and the full prompt text;
    - running the tests never rewrites `questions.json`;
    - TOON follows the TOON spec: valid nested headers, numeric-looking strings quoted, empty lists written the way the spec says. Don't edit R1's fixtures; note in the report that R1's TOON fixture has the invalid nested header.
