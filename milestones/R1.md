# R1: re-measure, then the Rust core

Read `RULES.md` and `SPEC.md` (v0.2) first. `SPEC.md` is the only authority on behaviour. Where it doesn't answer something, stop and ask (rule 5).

There are two parts, done in order.

## Part A: token re-measurement for v0.2

v0.2 changed the format from what M0 measured. Every data line now ends with `|`, null is `~`, and files are made of `schema:` blocks. Re-measure token cost with the Python M0 tooling.

1. Read the M0 measurement scripts in `C:\Users\Ashman Das\Documents\struct-py\bench\m0\`, especially the tokenizer helper and how it loads the four GGUF vocabularies on CPU. Copy what you need into `bench/r1/` in this repo, without copying model files.
2. Write v0.2 versions of the three M0 datasets: flat table (20 claims × 5 fields), nested fixed-shape (10 claims with a fixed `source` group), and nested variable (4 claims with notes and subnotes). The content must be the same as M0's fixtures in `struct-py\bench\m0\fixtures\`. Each file starts with its `schema:` line, follows SPEC.md exactly, and is written by hand or by a Python helper. The Rust encoder doesn't exist yet.
3. Count tokens on the same four tokenizers, and compare against M0's minified JSON and TOON fixtures (copy those files in as-is). Report Struct v0.2 *with* its schema line, since a file now always has one.
4. Separately, measure on all four tokenizers the cost of these line prefixes and endings: `|` + newline at the end of a line; `>` repeated 1–8 times at the start of a line, followed by text and by an index like `3|`; `~` as a whole field between pipes; and `\|` inside text.
5. Write `research/r1-remeasure.md`: plain-English method, tables, and a comparison with M0's numbers.

## Part B: the Rust core library

Build a Rust library crate named `structl` at the repo root (`Cargo.toml`, `src/`), standard library only, implementing **everything in SPEC.md**:
- **schema reading:** `schema:` lines, class definitions and reuse, field types (`str`, `int` as `i64`, `float` as `f64`, `bool`, `enum`, `record{...}`, `list[...]`), and the name rules;
- **decoding:** text to data. It returns blocks in file order plus warnings. An unneeded index produces a warning. Every error carries a line and column, and every rule in SPEC.md that says "is an error" produces an error;
- **encoding:** data to text, producing exactly one correct form;
- **`lookup(name)`**.

Design a clear public data type for decoded values, covering null, `i64`, `f64`, bool, string, enum label, record and list. Every public item gets a short doc comment saying what it does, in plain words.

### Tests (`cargo test --offline`)
- Every example in SPEC.md, decoded and checked, then encoded and checked byte for byte.
- One negative test, with the exact error, for each rule in SPEC.md that says "is an error".
- **Random round trips:** write your own small seeded random generator; no crates. Generate random classes up to 4 levels deep, mixing records, lists, enums and every scalar type, and random data for them. The data **must** include `~` nulls in every scalar type, records whose fields are all `~`, empty lists, values containing `|`, `\`, `~`, `>`, line breaks, leading and trailing spaces, and unicode, plus files with several blocks and reused classes. Check that `decode(encode(x)) == x` on at least 5,000 cases. Report the case count, and how many cases included each of the edge cases above.
- A float note: compare floats by their exact bits, and treat NaN as equal to itself in the round-trip check. Say how you did it.

## Done when
Part A's report is written; `cargo test --offline` passes; the round-trip suite covers 5,000 or more cases including every listed edge case.

The Part A tables; the test results with counts; any SPEC questions you stopped on (rule 5); and the plain-English transparency overview (rule 10).
